# 설계 결정 기록

각 항목은 확정된 결정입니다. 바꾸려면 여기에 새 항목을 추가하고 이전 항목을 "대체됨"으로 표시하세요. 코드만 바꾸고 이 문서를 그대로 두면 안 됩니다.

---

## D-001. 작업집합 소속은 작업이 갖는다 (다대다)

**결정** — `Task.taskSetIds[]` 가 소속의 유일한 출처입니다. `TaskSet` 은 `id` 와 `displayName` 만 갖고 작업 목록을 들고 있지 않습니다.

**이유** — 청소 작업집합은 오전·오후·주말 구성이 서로 다르지만 "청소기", "밀대", "정리" 는 셋 모두에 공통입니다. 작업집합이 작업 목록을 들면 같은 작업을 `vacuum_am`, `vacuum_pm`, `vacuum_weekend` 로 세 번 정의해야 하고, "청소기 2명" 이라는 사실이 세 곳에 흩어집니다. 방향을 뒤집으면 청소기를 한 번만 정의하고 `taskSetIds: ["cleaning_am", "cleaning_pm", "cleaning_weekend"]` 로 끝납니다.

**결과** — `requiredCount` 와 `conflictsWith` 는 작업집합과 무관하게 전역입니다. 만약 "오전엔 청소기 2명, 오후엔 1명" 같은 요구가 생기면 그때는 작업을 분리해야 합니다. 현재 요구사항에는 없습니다.

---

## D-002. 배타 검사는 작업집합 안에서만, 단 설정으로 확장 가능

**결정** — 기본값은 작업집합 내부 배타입니다. 한 작업자가 같은 시간대에 `청소` 집합과 `배치구역` 집합에 **동시에 배정될 수 있습니다.** `config.json` 의 `assignment.crossSetConflicts` 를 `true` 로 바꾸면 배타 검사가 시간대 전체로 확장됩니다.

**이유** — 예시에서 작업자 4명에 청소 집합만으로 슬롯이 8개입니다. 여기에 배치구역까지 배타로 묶으면 배정이 성립하지 않습니다. 실제 운영도 "청소도 하고 구역도 맡는" 형태로 보입니다. 다만 이건 추정이므로 스위치를 남깁니다.

**결과** — 엔진은 배타 검사 범위를 파라미터로 받습니다. 나중에 정책이 바뀌어도 재설계 없이 설정만 바꾸면 됩니다. 두 값 모두에 대해 테스트를 씁니다.

---

## D-003. 시간대에 속하지 않는 시각에는 다음 시간대를 보여준다

**결정** — `sched now` 를 점심시간이나 심야에 실행하면 빈 결과 대신 **다음에 오는 시간대**를 안내와 함께 표시합니다. 그날 남은 시간대가 없으면 다음 근무일의 첫 시간대를 보여줍니다.

```
지금은 12:40, 배정된 시간대가 아닙니다.
다음: 평일 오후 (13:00 시작)
```

**이유** — 빈 화면은 프로그램이 고장난 것처럼 보입니다. 점심시간에 오후 작업을 미리 확인하는 것이 실제 사용 패턴입니다.

---

## D-004. 인원이 남으면 남긴다

**결정** — 가용 인원이 슬롯 수보다 많으면 남는 사람에게 아무것도 배정하지 않습니다. 작업을 중복 배정해 억지로 채우지 않습니다.

**이유** — 필요 인원은 요구사항이지 목표가 아닙니다. 2명이면 되는 일에 3명을 넣는 건 낭비입니다.

**결과** — 라운드 로빈 커서는 그대로 전진하므로, 오늘 빠진 사람이 내일 먼저 배정됩니다. 이것이 공정성 기능의 씨앗입니다.

---

## D-005. 배정 스냅샷은 90일 보관 후 아카이브

**결정** — `state/assign-YYYY-MM-DD.json` 은 90일간 유지합니다. 그보다 오래된 것은 `state/archive/YYYY-MM.jsonl` 로 한 달치씩 합쳐 넣습니다. `sched prune` 으로 수동 실행하고, Phase 5부터는 시작 시 자동으로 확인합니다.

**이유** — 매일 파일이 하나씩 쌓이면 3년이면 천 개가 넘습니다. 반면 공정성 기능을 나중에 켜려면 과거 이력이 필요하므로 완전 삭제는 안 됩니다. 아카이브는 줄 단위 JSON 이라 나중에 집계하기 쉽습니다.

---

## D-006. 작업 완료 체크는 구현하지 않되 스키마 자리는 만든다

**결정** — 배정 스냅샷의 각 배정 항목에 `done: false` 와 `doneAt: null` 필드를 지금부터 넣습니다. CLI 는 이 값을 읽거나 쓰지 않습니다.

**이유** — 나중에 "이 작업 끝냈다" 기능을 넣을 가능성이 높습니다. 자리를 미리 만들어두면 그때 데이터 마이그레이션이 필요 없습니다. `priority` 필드와 같은 처리입니다.

---

## D-007. 동시 실행은 지원하지 않되 감지는 한다

**결정** — 한 데이터 폴더를 여러 프로세스가 동시에 쓰는 상황은 지원하지 않습니다. 다만 쓰기 작업 전에 `state/.lock` 파일에 PID 와 시각을 남기고, 이미 유효한 락이 있으면 경고 후 중단합니다. 락이 10분보다 오래되면 죽은 프로세스로 보고 무시합니다.

**이유** — 1인 사용이 전제입니다. 하지만 CLI 창을 두 개 열어놓는 실수는 충분히 일어나고, 그때 데이터가 깨지면 복구가 어렵습니다. 완전한 동시성 제어는 과하고, 락 파일 하나면 실수의 90%를 막습니다.

**결과** — Phase 5 에서 구현합니다. 그 전까지는 원자적 쓰기(D-008)만으로 버팁니다.

---

## D-008. 모든 데이터 쓰기는 원자적

**결정** — 임시 파일에 쓴 뒤 교체하는 방식만 사용합니다. `storage::atomicWrite()` 하나로 통일하고, 교체 직전 `.bak` 1세대를 남깁니다. Windows 에서는 `ReplaceFileW`, 그 외에는 `rename` 을 씁니다.

**이유** — 쓰는 도중 프로그램이 죽으면 파일이 반쯤 쓰인 상태로 남습니다. 스케줄러의 데이터는 손으로 다시 입력하기 번거로운 것들이라 손실 비용이 큽니다.

---

## D-009. 당일 급휴는 기존 배정을 지우지 않는다

**결정** — 배정 스냅샷이 이미 있는 상태에서 휴무가 등록되면, 그 사람의 배정을 **유지한 채** `absentAssignee: true` 플래그만 붙입니다. 자동 재배정은 하지 않고, CLI 가 미배정 건수를 알리며 `assign --force` 를 안내합니다.

**이유** — 조용히 재배정하면 이미 자기 일을 시작한 다른 사람의 작업이 바뀝니다. 사람이 이미 움직이고 있는 상태에서 화면만 바뀌는 것은 위험합니다. 재배정 여부는 사람이 판단해야 합니다.

---

## D-010. 우선순위는 스키마에만 존재한다

**결정** — `Task.priority` 는 JSON 에 존재하고 로드·저장되지만 배정 엔진은 읽지 않습니다. 값은 `null` 또는 정수입니다.

**이유** — 요구사항에 "지금은 구현하지 않고 일단 놔둔다" 고 명시되어 있습니다. 자리를 만들어두면 나중에 켤 때 파일 형식을 바꾸지 않아도 됩니다.

---

## D-011. 데이터 파일 위치는 실행 파일 옆을 기본으로

**결정** — 기본 경로는 실행 파일과 같은 폴더의 `./data` 입니다. `--data-dir` 옵션과 `SCHED_DATA_DIR` 환경 변수로 바꿀 수 있습니다. `%APPDATA%` 는 쓰지 않습니다.

**이유** — 압축을 풀면 바로 쓸 수 있고, USB 에 넣어 다닐 수 있고, 백업이 폴더 하나 복사로 끝납니다. 설치 프로그램이 없는 배포 방식과 맞습니다.
